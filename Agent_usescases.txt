## 1. Executive Summary

There is no shrink-wrapped "agentic AI for storage/compute/network" product that covers this stack end to end. This is a build effort layered on top of existing CSI/CSM tooling, OpenShift platform operators, and a centralized LLM gateway. Two constraints shape everything in this document:

- **No ODF/Ceph** means there's no internal self-healing/rebalancing intelligence to lean on — more operational judgment shifts onto agents watching the Pure/Dell layer directly.
- **Disconnected + LLM gateway** means vendor SaaS "AI" tools (Pure1, Dell CloudIQ/AIOps, Red Hat Insights-hosted features) are largely unusable as-is — they assume phone-home connectivity. Anything you want that capability from needs to be self-hosted against your own gateway and your own Prometheus/Thanos, not the vendor's cloud.

The guiding principle used throughout: **automate anything deterministic, especially failover/fencing/security-enforcement hot paths. Reserve the LLM for forecasting, cross-system correlation, and reasoning over unstructured material (matrices, KBs, logs).**

---

## 2. Classification Framework

Every Day-2 scenario in this document is tagged with one of three labels:

| Tag | Meaning | Typical implementation |
|---|---|---|
| **[Automate]** | Rule-based, deterministic, no reasoning needed | Operator, Ansible, GitOps, cert-manager, OPA/Kyverno |
| **[Agent]** | Needs synthesis across ambiguous or cross-system signals, or reading unstructured docs | LLM-backed agent with tool access |
| **[Agent→Automate]** | Agent diagnoses/recommends; deterministic layer executes once approved | LLM agent + guardrail engine + human approval gate |

Default posture: anything in a failover, fencing, or security-enforcement hot path stays **[Automate]** — you want determinism and speed there, not a reasoning pass.

## 3. Part A — Storage: Must-Have Agentic AI Use Cases

In priority order:

1. **Live-migration / RWX readiness gate.** Plain `pure-csi` against FlashArray is block/RWO only — RWX raw block for live migration needs Portworx Direct Access on top of FlashArray/FlashBlade. Dell's RWX story differs by backend (PowerScale/PowerStore file vs. PowerFlex block). An agent should check actual access mode before any migration or node drain instead of a human assuming it's fine — this is the single most common "why did my VM migration hang" surprise.

2. **Upgrade/interoperability pre-flight.** No live internet means no quick check of Red Hat's OCP support matrix, Dell's E-Lab Navigator, or Pure's compatibility guide. An agent that cross-references your *mirrored* copies of these matrices against target OCP + CSI driver + CSM Operator + array firmware versions before a change window is the highest blast-radius item on this list.

3. **Snapshot/backup/DR compliance + orphan reclaim.** With no Ceph/ODF fallback, every VM's protection posture rides entirely on Dell CSM Snapshot/Replication or Pure's snapshot policies/ActiveDR being correctly applied. An agent continuously diffs "VMs that exist" against "VMs with a current valid policy," and separately reclaims orphaned PVs/VolumeSnapshotContents quietly eating array capacity.

4. **Capacity forecasting.** Disconnected sites can't burst to cloud storage, and another shelf/array is a weeks-to-months procurement cycle. Trend thin-provisioning overcommit and PVC growth per namespace to flag "you hit the wall in N weeks" well before the array does.

5. **CSI/CSM health, drift, and cert/token rotation.** Watches CSM Operator CRs, controller/node plugin health, StorageClass parameter drift against baseline. Disconnected clusters usually can't use a public ACME CA, so CSM Authorization certs and Pure API tokens are tracked manually — flag expiry before it's a P1.

6. **Multipath/SAN incident correlation.** Bare-metal FC/iSCSI means path flapping is a real failure class. Correlate node multipath logs with CSI node-plugin and array-side port/host-group state into a plain-language RCA draft — this compensates for small on-site teams not having easy vendor remote support.

7. **Replication/DR failover-readiness.** For Dell CSM Replication or Pure ActiveDR/ActiveCluster: verify actual RPO/lag and runbook currency rather than assuming replication "is just running" — there's no cloud DR safety net behind a disconnected site.

8. **Golden image/DataVolume lifecycle.** CDI-based golden images need patch cadence and clone fan-out that respects per-volume snapshot limits on the array, avoiding a snapshot-slot wall mid-provisioning-wave.

### Architecture notes specific to the LLM-gateway / disconnected pattern

- The gateway endpoint has to live **inside the enclave** — an internally hosted/mirrored endpoint, not a call out to a public API. Red Hat's own OpenShift Lightspeed is built around the same shape: it points at an external-to-OpenShift LLM provider rather than shipping a bundled model, so this architecture choice matches where Red Hat itself is headed.
- Wrap Pure and Dell as **MCP tool servers**, not ad hoc scripts. There's already a public reference pattern for this against Pure's FlashBlade REST API (read-only first, then extended to take actions) — the same shape applies to Dell CSM/CSI objects and the PowerFlex/PowerStore/PowerMax APIs, though that side needs to be built in-house.
- **Read-only by default; human approval gate for anything destructive.** A wrong call against a production array is an incident, not a bad chat reply.
- **Mirror your knowledge base**, not just your registry. Compatibility matrices, KBs, and runbooks need to be in the RAG store and refreshed through the same process used for image mirroring.
- If already RHEL/Ansible-heavy, look at Red Hat's AgentOps framework and its agentic skill packs (RHEL/OpenShift/Ansible) before building fully bespoke — it doesn't ship Pure/Dell-specific skills, but it's the governance pattern Red Hat is standardizing on for this stack.

## 6. Part D — Agent Capability & Integration Matrix

### Platform layer (build once, shared by every domain agent)

- **LLM gateway access** with function/tool-calling support — not just chat completion
- **Embedding model + vector store** for RAG, self-hosted (pgvector/Milvus/Weaviate) since cloud embedding APIs won't reach a disconnected enclave
- **MCP tool servers**, one per integration, so the gateway calls a standard interface instead of bespoke scripts
- **Orchestration/agent framework** (LangGraph, CrewAI, Semantic Kernel, or custom)
- **Scoped credentials per tool** via a secrets manager (Vault, or OpenShift Secrets + External Secrets Operator) — never one shared credential across agents
- **Deterministic guardrail/policy engine** (OPA/Kyverno-style) between "agent proposes" and "action executes"
- **Human approval channel** reachable inside the enclave (Slack/Teams/ITSM)
- **Full trace logging** of every prompt, tool call, and action — mandatory for audit
- **Versioned knowledge corpus** (compat matrices, KBs, runbooks), refreshed through the same mechanism used to mirror images

### Domain-specific integration matrix

| Domain | Reads | Writes/Actions | Notes |
|---|---|---|---|
| Storage | Pure REST API, Dell CSM/CSI CRs + PowerFlex/PowerStore/PowerMax/Unity APIs, CSI metrics/logs | Same APIs (expand/snapshot/replicate), PVC/SC objects | Vendor SDK tokens, least-privilege per array |
| Compute | BareMetalHost CRs, Redfish per BMC, node-exporter | Redfish power/firmware actions, MCO, node API | Redfish auth differs by vendor (iDRAC vs iLO) |
| Network | OVN-K, NMState, MetalLB CRs, CoreDNS, network metrics | NNCP apply, network objects | SR-IOV device plugin state |
| Rightsizing | Prometheus/Thanos history, Kruize API | Resource patch (requests/limits), VM spec patch | Kruize is a tool the agent *calls*, not something it reasons from scratch |
| Platform lifecycle | OLM/CVO status, mirrored upgrade graph, ArgoCD | OLM subscriptions, ArgoCD sync | Mirrored upgrade graph is a hard disconnected dependency |
| Security/compliance | Compliance Operator results, audit logs, mirrored CVE feed | RBAC/SCC objects, remediation CRs | Mirrored CVE feed is itself a supply-chain dependency |
| Supply chain | oc-mirror logs, registry catalog | oc-mirror execution, registry GC | Effectively "internet health" for the whole cluster |

## 7. Part E — LLM Call Decision Framework

### Pipeline

```
Trigger
  → Gather signals                [no LLM]
  → Classify                      [LLM if novel, rules if known signature]
  → Plan + tool loop               [LLM, iterative]
  → Execute tools                 [no LLM]
  → Interpret results              [LLM]
  → Synthesize recommendation      [LLM]
  → Guardrail check                [no LLM, code]
  → Human approval                 [human]
  → Execute change                [no LLM]
  → Verify                        [no LLM, optional LLM summary]
  → Log / feed back to runbooks   [no LLM]
```

The LLM appears at exactly four points: **classifying** ambiguous signals, **planning** which tool to call next, **interpreting** messy/unstructured tool output, and **synthesizing** a human-readable recommendation. Everything else stays deterministic code, on purpose.

### Call the LLM when
- The signal-to-action mapping isn't hardcodable (correlating storage + network + compute logs, for instance)
- The input is unstructured (vendor docs, compat matrices, freeform logs, KBs)
- The output needs to be natural language (RCA draft, ticket text, recommendation)
- It's a first-time/novel situation with no matching runbook signature

### Skip the LLM when
- The mapping is a known formula (disk >90% → expand by X%)
- It's latency-critical or safety-critical (fencing, failover) — determinism beats reasoning
